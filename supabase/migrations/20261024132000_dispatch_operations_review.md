# Dispatch operations migration review

**Status: DRAFT ONLY / NOT APPLIED.** This local artifact has not contacted a remote database. No coordination migration, Cron job, fixture, account, commit, push, or deployment has been created by this draft. The core schema/RLS it targets are already applied to the current shared project under the user's separate authorization; do not apply this draft without new approval.

## What the draft implements

The migration defines `create_batch`, `split_batch`, `claim_sub_batch`, `rider_presence`, `heartbeat`, `validate_dispatch`, `confirm_pickup`, `deliver_sub_batch`, parent-status refresh, a shelter shock/reroute helper and trigger, `dead_man_sweep()`, and `expiry_sweep()`. It adds a private per-actor batch-request ledger. The donor UI now sends a UUID and retains the exact quantity/dependency/expiry payload in session storage until both create and split are confirmed; uncertain online responses can be retried with the same key. No offline write queue is added.

The splitter subtracts active demand reservations, checks dependency compatibility, limits child quantities to 40, bounds assigned chunks by recently present available rider capacity, and represents leftovers as unassigned `at_risk`. All six shelter-demand reservation calculations include shelter-assigned `at_risk` children, preventing unresolved/stale cargo from being double-allocated; an unassigned at-risk remainder with no shelter reserves no specific shelter. Rider presence is a rider-owned RPC because installed rider rows default to `offline`. Claim requires recent presence; same-rider claim retries reject expired/stale assignments and closed pickup windows before success. Active heartbeat runs while online and cannot revive a heartbeat older than 90 seconds. Pickup rechecks the five-minute confirmation deadline, liveness, expiry, shelter resources, and remaining demand; repeated pickup confirmations also reject expired or stale in-transit loads. Delivery is idempotent for a confirmed prior delivery, decrements demand once, and fails closed if the remaining demand would fall below other reservations. Pre-pickup stale claims are reoffered only if their shelter still has compatible resources and sufficient unreserved demand; otherwise they become `at_risk`. Stale in-transit cargo becomes `at_risk` and the rider moves to `needs_check`. The expiry sweep marks expired open parents with no children `fully_spoiled` and writes a parent-level audit row.

The RPC migration does **not** schedule recurring jobs. A separate opt-in draft, `20261024132001_dispatch_sweep_schedules_draft.sql`, defines `dead_man_sweep()` every 30 seconds and `expiry_sweep()` every minute. Applying that file creates persistent data-mutating Cron jobs and needs its own review/authorization. No job is active from these local drafts. Supabase's official Cron guide and the pg_cron project document sub-minute intervals such as `30 seconds`; see [`docs/reference/supabase-cron.md`](../../docs/reference/supabase-cron.md).

All app-callable functions use `SECURITY DEFINER` with `SET search_path = ''`, schema-qualified application objects, explicit actor/role/ownership checks, and explicit execution grants. Internal helpers, triggers, and sweeps are revoked from `PUBLIC`, `anon`, and `authenticated`; the Cron runner still depends on applying as a role allowed to execute the protected sweep functions. The migration uses a single transaction-scoped advisory lock to serialize coordination writes and then locks rows in deterministic parent → child → shelter → rider order.

## Deliberate omissions and known limits

- **No judge/failure-injection RPCs.** The shared project has no proven demo-row isolation. An admin role check alone is not enough to protect live shelter or rider state. Add those controls only in a confirmed isolated project or after a reviewed test-row boundary exists.
- **No road ETA.** The schema has points but no road graph, routing service, speed model, or ETA field. Rerouting uses straight-line PostGIS distance, fresh rider coordinates, dependency compatibility, unreserved demand, and a five-minute expiry buffer. It records `eta_checked: false`; this does not prove a route is reachable before spoilage.
- **No at-risk recovery RPC.** Stale in-transit cargo requires human verification, but a trusted recovery/reattribution workflow is not yet defined. Keep it non-claimable until such a workflow is reviewed.
- **Shelter state changes are limited.** The trigger handles a positive-to-zero demand transition. No user-facing shelter demand/resource mutation RPC is included. If trusted SQL lowers demand but leaves a positive value that cannot cover existing reservations, pickup/delivery validation fails closed and requires manual reconciliation; broader positive-demand/resource-loss handling remains incomplete.
- **Global serialization tradeoff.** One advisory lock is conservative and may limit throughput. It needs load/concurrency testing before production use.
- **No live test.** `pglast` validates top-level SQL grammar, not Postgres runtime compilation of PL/pgSQL bodies, catalog privileges, trigger behavior, Cron ownership, RLS bypass, or concurrent invariants. No disposable PostgreSQL/Supabase instance has been started.
